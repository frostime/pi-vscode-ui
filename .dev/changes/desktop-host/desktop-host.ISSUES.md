# Desktop 宿主：问题与期望

本清单保留需求、担忧与未决事项，不按执行顺序排列。记录不等于承诺全部实施；推进顺序和当前状态只维护在 [顶层计划](desktop-host.ORCH.md)。需求边界以 [DEV-SPEC](desktop-host.DEV-SPEC.md) 为准。

## I01：需要简单的本机 Pi GUI

来源：用户不喜欢现有 Pi Desktop App 的臃肿，希望基于现有插件增加简单 GUI。

期望：复用现有聊天能力，使用本机已安装 Pi。轻量优先指功能和操作简单，而非安装包或基础内存最小。Electron 是当前建议，不是已验证结果。

## I02：插件开发者不需要考虑 Desktop

来源：用户明确要求开发 Pi VS Code UI 时，可以装作不知道 App 需求，只按一定规范开发。

期望：插件既有功能保留，VS Code 专属功能可以独立增长。共享代码只依赖明确边界；Desktop 不把缺失能力的适配责任交给插件开发者。

待明确：边界如何用导入检查、测试、包入口和开发命令落实；共享契约变化时由哪一侧接续适配。

## I03：复用不能引入混乱的代码组织

来源：用户关心现有主要代码位于 apps/vscode，Desktop 应怎样导入，以及拆包是否比 Wrapper 更混乱。

期望：共享实现只有一份，依赖入口清楚，插件本地开发不需要构建或运行 Desktop。

首步已选择组合路线：先在原位置建立薄宿主输入，再提取一个共享包的 core/shared。UI/连接的归属与入口仍待后续。分成后端/UI/契约多个包不作为默认方案，只有隔离或构建证据说明必要时才展开。代码物理位置与宿主抽象是两个不同决定；不能以大量搬文件代替职责划分。

## I04：Project 保存与切换

来源：用户希望 App 提供保存、切换 Project 等管理功能，并确认切换只改变前台 UI。

期望：可以回到已保存的项目，切换不影响后台 Session 的进程和工作目录。

待明确：Project 标识、保存字段、项目移除语义、界面形式，以及工作树与多根目录在 Desktop 中的表示。不得提前把最近项目列表或某种固定布局写成已确认设计。

## I05：多个 Session 并行运行管理

来源：用户希望最好支持多 Session 并行；现有插件已经支持独立 Pi 进程执行。

期望：不同项目的会话可以同时运行，切换前台后仍能查看其运行和等待输入状态。

待明确：一个项目一个长期存活会话集合，还是应用级集合；切换、新建、恢复与未提交会话的策略。现有工作区校验和 Provisional 清理不能直接当作 Desktop Project 切换规则。

## I06：两端不支持的宿主集成需要有边界

来源：用户允许强依赖 VS Code 的功能先禁用，以后再提供替代。

期望：Desktop 可暂不提供编辑器选区、当前文件、外部草稿编辑、文件定位或 diff 等集成，不限制插件；复制、外部链接、普通文件搜索等应按实际成本判断。

待明确：首版能力清单，入口隐藏与动作拒绝方式，以及宿主能力如何与 Pi/OMP 运行时能力分开。Pi 的阻塞输入交互不能与 IDE 功能一起粗略关闭。

## I07：切换时不能误处理其他 Session 的数据

来源：多项目与多 Session 目标；初步审计发现同步、草稿和批注清理依赖当前展示模型。

期望：异步结果、草稿、批注和输入请求按 Session 身份处理，前台过滤不被当作后台会话删除。

待明确：Desktop 的草稿权威与挂载生命周期；现有连接目标校验和快照/增量恢复如何复用。不能通过取消校验来简化单窗口迁移。

## I08：未来 VS Code 状态 Pi extension 不受阻碍

来源：用户计划以后增加 Pi extension，主要向 Agent 告知当前 VS Code 状态。

期望：状态采集和扩展接线可以留在 VS Code 端，由宿主按启动提供；Desktop 不必实现同等能力。

待明确：宿主专属扩展的启动接入方式，当前窗口与 Session 项目状态的范围，以及独立/全局安装时通信服务缺失的行为。此项不要求现在实现状态工具或完整 IPC 框架。

## I09：共享化后插件行为保持不变

来源：用户要求保持插件干净并并行维护；现有模块契约已有复杂状态和同步规则。

期望：共享化不退化既有 Pi/OMP、工作区/远程、恢复、Fork、树导航、临时会话、侧边栏/标签页及草稿交接行为。

用户新增检查点要求：先完成首步重构并提供可运行候选，由用户亲自运行确认功能正常后才能继续；自动检查不能替代此反馈，发现回归则在当前阶段修复。

待明确：后续迁移所需的局部测试、Extension Host 验证和构建证据。R1 的自动验收已在实施 Ticket 指定。Desktop 首版是否提供 OMP 不由现有插件兼容性自动决定。

## I10：应用生命周期与恢复范围未定

来源：后台执行目标与对话中提出的退出建议。

待决定：窗口关闭与实际退出的区别、是否常驻、退出时进程处理、启动时恢复/自动启动策略、元数据保存范围。无托盘、退出停止进程只是建议，用户尚未确认。

## I11：Desktop 的运行与发布范围未定

来源：Electron 使用当前本机 Pi 的候选方案尚未实测。

待确认：首版支持系统、本机 Pi/Node 定位及 GUI 启动环境、主题和字体、Svelte/CSS/资产的包导出与构建、IPC 安全和最终打包。不能用终端中能启动 Pi 替代 Desktop 环境验证。

## I12：投入规模需要阶段证据

来源：用户希望先判断可行性与效果预期，再按 project plan 推进，允许后续继续调研。

期望：先获得边界专项调研和真实最小链路，之后再估算完整重构成本和首版范围。保持检查点，发现共享方案依赖大量复制或宿主分支时重新规划，不以“完成所有抽象”作为继续条件。
