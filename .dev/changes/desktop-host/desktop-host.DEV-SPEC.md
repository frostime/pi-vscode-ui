# Desktop 宿主：目标与边界

本文件记录本次讨论的目标和共识，不改变现有模块契约。执行入口是 [顶层计划](desktop-host.ORCH.md)，未决问题见 [Issues](desktop-host.ISSUES.md)。

## 问题

用户需要一个基于现有 Pi VS Code UI 的简单 Desktop GUI，不希望另做一套臃肿客户端。应用使用本机已经安装的 Pi，尽量复用现有聊天体验和会话逻辑。

用户尤其关心维护方式：开发 VS Code 插件时，可以不考虑 Desktop 的存在，只需遵守清楚的模块规范。共享化不能让插件开发者承担两端功能适配，也不能让代码组织变得混乱。

## 已确认目标

- VS Code 插件与 Desktop 并行维护，插件现有功能不能因共享化而退化。允许必要的代码提取、接口调整和宿主接线，不要求冻结插件源码。
- Desktop 使用本机 Pi，不以捆绑 Pi 为目标。轻量主要指功能和操作简单，不优先追求最小安装体积或基础内存。
- Desktop 提供项目保存、选择和切换能力，并支持多 Session 并行运行管理；具体管理界面和保存字段尚未决定。
- 切换 Project 只改变前台 UI，不停止或重定向后台 Session。已有 Session 保持自己的工作目录。
- Desktop 不支持的 VS Code 集成可以暂不提供，或以后提供替代；不能反过来限制插件增加专属功能。
- 未来可能增加向 Pi 告知 VS Code 状态的 Pi extension。这是需要保留的接入需求，不是本次已经授权实现的功能。

## 已确认的首步重构检查点 R1

用户已接受先解耦完整单会话 Runtime，再提取一个共享客户端包的 core/shared。Registry 只调整创建接线；Persistence、UI/Bridge 和 sidebar/panel 的产品策略不在首步改变。包名与局部接线由实施者决定，不增加 Desktop 依赖或无消费者的扩展接口。

R1 必须交付可运行的插件候选和自动验证证据，随后由用户运行确认原有功能正常。用户最初要求确认前不继续后续阶段。随后用户明确允许先检查卡点，在无需新增产品取舍时提前推进，次日再验收。因此可以在独立候选中先做保持插件行为的 UI/Bridge 准备；这项授权不免除 R1 人工验收要求，实际验收状态以顶层计划为准。发现回归则优先修复。R1 不是 M1，也不代表 Desktop 已完成。

## 后续方案建议，尚未定稿

- 采用 Electron，优先复用 Node/TypeScript 后端；这是当前规划的候选路线，尚无 Desktop 运行验证。
- 用少量、面向实际能力的宿主接口和依赖注入隔离 VS Code，不模拟整套 VS Code API。
- 共享代码只维护一份，两端通过明确入口使用。首步一个包的 core/shared 已确认；浏览器 UI、样式和连接模块的入口及迁移范围在用户通过 R1 后再确定。
- 共享聊天主体，不强求两个产品使用同一应用布局。Desktop 的项目管理留在自身外壳。
- Pi 继续拥有对话文件和运行状态；Desktop 不另建对话内容数据库，只保存必要的管理元数据。

上述建议不能仅因写入计划就视为用户已确认的正式接口或持久化方案。

## 行为边界

### 插件开发与兼容

开发通用聊天或会话功能时，不需要添加 Desktop 专用分支。开发 VS Code 专属集成时，不需要同时实现 Desktop 版本。Desktop 自己承担适配责任，但共享契约改变后仍可能需要跟进；本次不承诺任何共享改动都自动兼容另一宿主。

现有插件的工作区配置、远程 Extension Host、会话恢复、Fork、树导航、临时会话、侧边栏与标签页行为以现有契约为准。Desktop 的产品选择不能静默改变这些行为。

### 会话、交互与宿主能力

会话生命周期不得由前台 Project 的显示状态决定。后台会话的消息、草稿和输入请求必须仍属于原 Session，不能因过滤前台列表而被当作删除。

不支持的集成不能伪装成成功。具体隐藏入口、拒绝动作及提示方式在能力清单确定后设计。Pi 的阻塞输入交互与编辑器集成是不同能力，不能通过关闭所有交互来规避迁移。

### Pi 与文件

保持一 Session 一 Pi 进程的基础。共享化不新增全局执行锁、文件写入拦截或冲突解决承诺；Pi RPC 与对话投影的现有职责继续保留。

VS Code 专属 Pi extension 可以由插件宿主按启动加载并提供通信接线，Desktop 不必加载或实现它。Pi extension 运行在 Pi 进程中，不能直接使用 VS Code API。

### 尚未决定的责任

首版操作系统范围、窗口关闭与实际退出行为、是否常驻托盘、启动时哪些 Session 自动运行、管理元数据结构及恢复规则，均未确认。不能从“切换 Project 不停止后台”推导出“退出 App 后仍运行”。

## 阶段完成判断

以下用于评审阶段结果，不表示本轮授权实施全部功能：

- 专项调研给出可比较的边界方案、最小迁移路径和证据，用户能够确认或否决，不需要先完成大规模重构。
- 最小纵向版本中，原插件和 Desktop 实际使用同一份会话逻辑、对话投影和聊天组件，而非复制实现或互相依赖内部文件路径。
- 最小纵向版本能使用本机 Pi 发送消息、展示流式结果、停止运行和恢复一份已有历史；原插件相关行为有验证证据。
- 多项目阶段中，至少两个 Project 的 Session 可并行运行，切换前台不改变后台运行，结果和输入请求不串 Session。
- 插件能够独立开发和构建，不要求运行 Desktop；共享代码的宿主依赖边界可由检查或测试约束。
- 首版功能、平台及生命周期范围经用户确认后，补充真实使用与打包验收，不提前承诺全部插件功能等价。

## 术语

- **Project**：Desktop 管理的本机项目入口；不是要求共享核心新增的全局项目模型。
- **Session**：拥有自己工作目录与 Pi 进程生命周期的会话。
- **宿主接口**：共享逻辑需要的外部能力，如配置来源、交互或消息传输；不等于 VS Code API 的同名模拟。
- **最小纵向版本（M1）**：从宿主启动、共享逻辑到聊天 UI 的一条真实运行链路，不是完整 Desktop 首版。
