# Desktop 副产品：目标与质量标准

## 目的

现有 VS Code 插件已经顺手，但零散项目仍需要在终端中多开 Pi。要复用这些已有优势，提供一个可独立使用的 Desktop App。

**VS Code 插件是主产品，Desktop 是同步维护的副产品。不是把项目迁成桌面优先，也不是另写一个客户端。**

## 期望的产品效果

- Desktop 使用本机 Pi，无需打开 VS Code；提供多开 Pi 终端的 GUI 替代体验。
- 对话是主体，目录导航从简，默认显示全部已打开的 Pi。查看或切换一个 Pi 不停止其他 Pi，也不改变已有会话的 cwd。
- 保留现有插件已经顺手的聊天与会话能力，包括 New/Resume 等已有操作；不因增加 Desktop 就另造管理流程或内置 IDE。Pi 仍拥有对话文件。

## 架构级质量要求

通用 UI 和会话能力只维护一份，两端实际消费同一实现。允许外层布局不同，不允许用复制、重写或手工同步实现“双端相似”。宿主提供所需能力，不模拟整套 VS Code API。

| 开发中的改动 | 应有的维护效果 |
|---|---|
| 消息、工具展示、输入框等通用 UI 细节 | 改一处自然进入两个产出，不需要再向 Desktop 移植 |
| VS Code 专属集成 | 可以只改插件，不要求 Desktop 提供等价功能；包括未来向 Pi 提供编辑器状态的扩展 |
| 共享契约、宿主能力或会话行为 | 能明确识别 Desktop 是否需要适配，并有对应兼容检查，不能默默分叉 |
| Desktop 专属窗口、目录入口等 | 调整留在 Desktop，不反过来改变插件的既有约定 |

这些边界必须由代码归属、依赖限制和检查支撑，不能靠每个开发者熟悉两端实现。插件仍可独立开发、构建和使用，已有行为不因共享化而退化。

**完成不只是出现桌面窗口：** 要实际证明一次通用 UI 修改进入两个产出，并在共享实现上跑通真实 Pi 的发送、停止和历史恢复。只有两张相似的界面、插件测试通过或原型可操作，都不足以证明目标达成。

## 尚未决定

集合与草稿归属、Desktop 缺少宿主能力时的具体处理、关闭/重开恢复、平台范围，以及 Header 与目录导航的具体组合，仍需按实现所遇到的取舍确认。本文件不预定组件接口或完整布局。
