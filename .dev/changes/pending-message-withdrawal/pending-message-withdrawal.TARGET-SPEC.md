# Pending message recovery — Change Spec

## 1. 目标与文档状态

实现 GitHub [issue #10](https://github.com/frostime/pi-vscode-ui/issues/10) 的保守第一版：用户可以一次性取回当前会话的 Steer、Queue 待处理内容，以便编辑后重新发送，而不停止正在运行的 agent。

Issue 首选逐条撤回，但明确接受 withdraw-all 替代。用户已确认第一版采用批量操作，支持 Pi 和 OMP，接受 Pi 与 TUI 同级的尽力取回语义，以及附件的保守边界。

本文件记录目标、行为与架构约束，不表示功能已经实现。具体 UI 原型仍待用户评审；实现形状见同目录 `pending-message-withdrawal.SHAPE.md`，目前也未锁定。已验证的运行时事实与版本见 `RESEARCH.md`，不能把其中的实验脚本当成产品接入。

## 2. 功能范围与正常路径

- 一个批量入口同时处理 Steer、Queue，不要求用户逐条操作。
- 操作仅作用于请求来源所对应的会话：sidebar 中是发起时的会话，editor tab 中是该 tab 固定的会话。不能因为等待过程中切换了 sidebar 选择，就操作或回填到另一个会话。
- 已登记但尚未完成入队确认的排队提交，与取回之间必须有明确先后关系，不能先清空、再让本应被处理的输入迟到入队。
- 本次取回处理一个有界的候选集合，不持续追赶之后产生的新输入。处理中须防止重复执行及与同会话新排队提交冲突，但不等待整个 agent turn，也不阻塞其他会话。
- 操作完成后，将能够恢复的内容放回原会话的输入框，不自动发送，不改变当前 Steer/Queue 发送选择。
- 成功、部分成功、未能移除和结果不确定须有符合事实的反馈；不能统一显示“全部撤回成功”。

正在运行的 agent 继续工作。不得通过 abort、重启进程、暂停整轮执行，或“清空后重发其他消息”来模拟取回。

## 3. 两种运行时的行为边界

### Pi：尽力取回文本

- 支持一次性取回两类待处理文本，但不保证已经被 Pi 取出的消息不再执行。
- 操作结果必须准确提示这一限制，不能把返回文本当作逐条撤销确认。
- 若取回后 Pi 仍投递了其中的消息，该消息必须正常出现在对话中。不得隐藏实际投递，也不得将它显示成另一条新提示词。
- 任一待处理输入含图片附件时，第一版禁用整批取回，并给出原因，不提供会悄悄丢图的文本恢复。

### OMP：恢复确认移除的部分

- 只将后端确认移除的内容计入取回结果；没有移除成功的输入仍沿原有运行流程处理。
- 原始操作按文本匹配，不提供 FrostPi 本地消息 ID 的精确删除保证。第一版不宣称能够指定第二条同文消息，也不暴露逐条撤回 UI。
- “未移除”不自动等价于“已投递”。只有实际收到的运行时事实才能使消息成为对话记录。
- 批量操作中途失败时，已经确认取回的部分仍须交付给用户，不能被后续异常抹掉。结果不确定时不自动重试破坏性操作，以免移除另一条同文消息。

统一的是批量入口及结果模型，不是两种后端的确认强度。UI 应消费功能结果与可用性，不自行判断 Pi/OMP 种类并拼接 RPC 行为。

## 4. 草稿与附件

### 草稿保留

- 回填以完成时原会话的最新草稿为基础，保留等待过程中继续输入的内容和已有附件，不用操作开始时的旧快照覆盖它。
- 取回内容只应用一次；Host 已完成的合并不能由 UI 再合并一遍。
- 回填不自动提交，也不自动重建多条消息各自的投递类型。
- 保留现有 Host-owned editor tab 草稿及 tab→sidebar 交接合同，包括取回尚未完成时关闭 tab 的情况。
- 普通 sidebar 草稿仍是 Webview-local；本次不引入跨 Webview 销毁、应用重启的持久恢复保证。
- 只在原会话仍由当前界面展示时请求相应输入框焦点，不抢走无关会话的焦点。

### 附件保留与限制

- OMP 正常返回的可用图片随文本一起恢复，保留原草稿附件，遵守已有数量、单图大小和格式限制。
- 不能通过截断附件数组静默丢图，也不能按同文消息猜测旧图片并补回。
- 后端报告图片缺失，或宿主传输限制导致无法完整交付时，必须明确显示部分恢复/失败，不能声称完整恢复或让请求一直停留在处理中。
- 文本编辑不因取回而整体冻结；处理中可限制发送及新增附件，以保持操作与容量边界明确。

## 5. 已确认的架构与质量约束

### 功能协调只有一个所有者

- 使用专用的 `QueuedPromptRecovery` class，每个 SessionRuntime 当前的子进程生命周期对应一个实例。它负责提交确认等待、取回互斥、Pi/OMP 取回流程、部分结果和过期结果处理。
- `SessionRuntime` 只做实例生命周期、必要的提交确认接入、动作转发和状态投影；不继续堆积整段恢复事务逻辑。
- 不再叠加 Hook、Manager 或通用任务/队列框架。恢复 class 不接受整个 SessionRuntime 并反调它的一组私有方法。
- 对话回合、待处理气泡和持久身份仍由 `ConversationProjection` 负责；草稿仍由现有 Host cache / Webview draft 模块负责。恢复 class 不接管这些模块的内部状态。

### 运行时和桥接边界

- 只有等价的名称/格式差异可以在 RPC 消息层转换；本功能的状态相关差异留在产品层，不能把一次 Pi 清空伪装成等价的 OMP 多次删除。
- 后端事实仍由 Pi/OMP 提供，持久对话仍以 `get_entries` 的 entry id 为权威；不通过正文、图片或时间戳相等发明新的消息身份规则。
- Session 重启、进程替换或 Session 移除后，旧操作的结果不得写入新的运行实例。
- 新 bridge 请求继续经过完整校验和来源会话授权，结果保持关联，不增加跨会话权限。
- Host-owned 草稿只由 `ComposerDraftCache` 变更；普通 Webview 草稿沿现有 draftSync/revision 路径合并，不绕过版本或双写。

### 双产品与副作用范围

- 功能落在共享 `apps/pi-client`，VS Code 为参考交互环境；Desktop 复用同一应用实现，不建立专有队列或第二套 Composer。
- 宿主现有限制由对应适配边界负责，允许必要的有限桥接适配；不借此修改 Desktop 原生壳、打包或发布流程。
- FrostPi 不直接修改 Pi/OMP 安装内容或会话文件，Pi/OMP 自行维护会话持久化的职责不变。不新增提示词/附件持久化存储，不将正文、图片字节或凭据写入日志。

## 6. 验收：解决、好用与可证实

以下是行为验收，不是要求每行分别建立一组重复测试。Agent 选择能抓住具体回归的最少测试；同一规则不按函数或文件重复证明。

| 场景 | 合格结果 | 不合格示例 |
| --- | --- | --- |
| Steer、Queue 同时排队 | 批量处理两类内容，保留草稿，不自动发送，当前运行继续 | 只处理一个队列，或为了取回停止 agent |
| 入队确认与重复点击交错 | 已登记提交不被过早清空漏掉，同次操作不重复执行 | 回填后又迟到入队，或同文内容被重试误删 |
| Pi 旧消息迟到、随后又有新消息排队 | 对话展示真实旧消息，新提示词身份与排队状态不被冒领 | 用新提示词文本显示旧事件，或把新气泡错误消费掉 |
| OMP 部分成功后失败 | 已确认部分仍能恢复，其他输入不被冒称已撤回 | 后续异常使先前取回的内容消失 |
| 等待中编辑、切换 Session 或关闭 tab | 使用最新草稿，回填到原会话一次，遵守既有交接 | 覆盖新输入、写错会话、重复插入或抢无关焦点 |
| 图片缺失或超限 | Pi 含图时不执行；OMP 正常恢复图片，无法完整恢复时明确反馈 | 静默丢图、猜错图片，或永远显示处理中 |
| 请求目标不是来源会话 | 拒绝操作，不修改其他会话的队列和草稿 | 仅凭浏览器传来的 Session id 执行 |

完成还要求：

- 前端入口、Host、恢复协调、会话投影和草稿回填真正接通。不能用一个孤立按钮测试加一个独立 RPC 实验冒充完整接入。
- 核心反例先证明能够让错误实现失败，尤其是迟到消息冒领、重复取回、部分成功被后续错误抹掉。
- 不为薄转发、getter/setter、机械字段复制或私有调用次数单独铺测试；不复制实现算法计算 expected，也不以无关的大段 DOM 快照替代行为断言。
- 检查现有会话发送、Stop、草稿交接及两端共享构建没有被本次改动破坏。

**验证归属：** Agent 负责源码、自动化交互、真实 Pi/OMP 隔离运行及回归证据，并在交付时明确列出已验证和未验证项。用户负责按钮位置、交互手感和文案偏好等不可替代的主观判断；常规功能验证不转交给用户。

## 7. 非目标与尚待确认事项

非目标：逐条精确撤回、取回后自动重发、重建原多条消息的 Steer/Queue 类型、修复上游队列 API、增加通用恢复系统、引入新的持久化或 IPC 分块协议。#11 的用量入口和百分比修复也不属于本次工作。

尚待确认/解决：

1. **UI 原型评审：** `prototype.html` 当前建议在气泡组顶部放入口、将取回文本以前置空行合并到草稿，并提供就地反馈。这些具体形式尚未获确认，不作为已定交互要求。
2. **迟到事件投影方案：** 已复现现有 FIFO 规则会消费另一条新提示词；SHAPE 中的局部修复方案尚未验证。实现必须满足第 3、6 节的身份与展示目标，不能以用户接受 Pi 尽力语义为由放宽它。

具体文件、接口草图、量级和漂移界限由 `pending-message-withdrawal.SHAPE.md` 记录；技术路线如果变化，应修改该草案或重新评审，不能倒改本文件的目标来迁就实现。
