# Pi Session Lifecycle

Read with `apps/pi-client/src/host/SessionRegistry.ts` for entry/collection lifetime and `apps/pi-client/src/core/sessions/SessionRuntime.ts` for the Pi child and turn lifetime. These lifetimes are not interchangeable: a registered Session may have no live process, a ready process may still be loading history, and a view may disappear while its Pi continues working. The constraints below preserve those distinctions; host adaptation and projection details have their own contracts.

## Identity and execution do not follow presentation

Registry's FrostPi Session id identifies an application entry, not the Pi session id, a transcript entry id or a process instance. Stop and restart retain that application identity. A Runtime may have no child while stopped, but cannot own multiple live children. Pi owns JSONL and conversation persistence; FrostPi must not rewrite those files.

Views are disposable projections, not Runtime owners. Clearing foreground selection or closing a Session Tab does not close the underlying Session. Selection is not universally side-effect-free, however: activating a stopped persistent Session can start it, and switching away can discard an unretained Provisional Session under the policy below. Explicit Close disposes/removes the application entry without deleting Pi-owned history. Close/restart must confirm interruption when the Session is streaming or has pending extension input.

An existing Runtime's cwd and configuration scope must not follow later editor, Project or foreground changes. New/Resume uses a Host-chosen, validated workspace/worktree; the browser cannot supply a cwd. External worktree configuration comes from its authorizing workspace root. Before restoring or starting a stopped external Session, refresh directory authorization: confirmed removal may drop metadata, but failed discovery neither proves removal nor authorizes a start. Directory/alias resolution belongs to `apps/pi-client/src/host/sessions/SessionWorkingDirectories.ts` and the [catalog contract](catalog/session-catalog.SPEC.md).

VS Code's default anchor is the active editor's workspace folder, otherwise the first root; New/Resume does not aggregate unrelated repositories. Desktop Project ownership and selection policy are in `apps/desktop/SPEC.md`. Neither policy creates a second lifecycle or changes an already-running Pi's context.

## Readiness and turn completion

Registry serializes starts and complete-history loads in separate queues. A long history load must not hold up another process's startup, and neither queue serializes agent execution. Concurrent Pi turns remain independent; FrostPi adds no global execution lock or file-write interception.

Process readiness alone is not admission to every operation. Prompt/model actions cannot bypass queued/starting process state. Fork, tree navigation and FrostPi's own commands must not start during compaction even if process status is ready. A prompt submitted during compaction is accepted as a Steer/Queue bubble instead. `/compact` itself is answered once Pi reports `compaction_start` (or refuses), not when compaction ends, so the submitting Composer is free during it; a later failure is reported by `compaction_end`. Pi refuses prompts during a manual compaction (`compaction_start` reason `manual`, or an unknown reason while no run is active), so the Runtime holds them, as Pi's terminal UI does, and submits them in order with their streaming behaviour at `compaction_end`: the first starts a run or joins one, the rest queue. An automatic compaction runs inside a Pi run, so a prompt goes straight to Pi's queue. Abort, stop and process failure drop held prompts with the rest of the queue projection; extension commands still go to Pi immediately. Compaction progress is transient state, not a new persisted turn; Pi's own summary entries still define durable history boundaries.

Model-selection flags in the configured Pi arguments (`--provider`, `--model`, `--thinking`) are defaults for new conversations. A launch that resumes a saved session drops them so Pi restores the session's own model and thinking level; `--models` stays (`configuredLaunchArguments`).

History readiness is separate. A resumed process can become ready before its entries are loaded: submission remains blocked during queued/loading history, while Fork and tree navigation require fully loaded entries. Deferred or failed history does not by itself fail the child; large-file loading can wait for explicit user action. The history replacement must preserve concurrent deliveries without losing or duplicating content; `SessionRuntime.#loadHistoryInternal` owns capture/replay mechanics, and the [live-reconciliation contract](../core/conversation/conversation-projection.SPEC.md#live-reconciliation) owns reconciliation.

For agent turns, prompt RPC success means acceptance, not completion. `agent_end` closes an attempt; retries or compaction continuation can still belong to the same user turn. The normalized `agent_settled` event closes that turn. Only a successfully completed, non-aborted agent turn may issue the normal-completion notification, once. Error turns, compaction, history refresh and repeated state updates must not manufacture one. A state read that Pi answered before a later `agent_start` is stale and must not mark that turn idle. [Tool finalization](../core/conversation/conversation-projection.SPEC.md#unresolved-tool-results) belongs to projection rather than failing a whole Session for every tool error.

Input/failure attention is separate from normal completion: notify on the first pending input or transition into failed state, not every later view update. `SessionRegistry.#showSystemNotification` owns preference/focus gates and native-delivery fallback; do not turn ordinary refreshes into new notification events.

Some runtime commands finish without agent-turn events. Their classification and idle reconciliation are local to `SessionRuntime.#resolveImmediateExtensionCommand` and `#finishImmediateExtensionCommand`. If a known extension command exceeds the prompt deadline while its process remains live, report completion as unconfirmed, not a failed process or proven completion. OMP's per-submission results likewise cannot settle other queued work; its stateful adapter is `apps/pi-client/src/core/sessions/OmpPromptCompatibility.ts`. Command admission and visible invocation rules belong to the [Composer contract](../ui/features/composer/composer.SPEC.md), not transport aliases.

Steer/Queue bubbles are local projections of runtime-owned delivery, not independently cancellable jobs. Bulk recovery is owned by one process-scoped `QueuedPromptRecovery`: it orders admitted queue submissions before mutation, blocks duplicate recovery without locking an agent turn, and rejects old-process results. Pi clear-all is best effort and text-only; OMP first-match removals restore only confirmed results, retaining earlier successes after a later failure and never retrying an ambiguous mutation. Recovery of Pi's queue cannot start during compaction, since Pi may already have taken a queued message for the next turn, or start a stopped child. Prompts the Runtime holds through a manual compaction are FrostPi's own: when every pending bubble is held, recovery withdraws them at once, compaction or not, with their images, as a confirmed outcome, and it does not abort or rebuild a queue. Removing a local bubble or receiving Pi's text does not prove cancellation. Abort, stop and process failure clear the transient queue projection. Promotion/turn ordering follows the [turn-lifecycle contract](../core/conversation/conversation-projection.SPEC.md#turn-lifecycle); keyboard bindings stay in the Composer contract.

Blocking extension input belongs to its Runtime/request, never whichever Session is now visible. Answering, timeout or explicit cancellation resolves it; hiding its UI does not. Abort/stop/restart cancel pending input rather than auto-confirming it. The [extension UI contract](../core/extension-ui/extension-ui.SPEC.md) owns method-specific responses and presentation.

## Committed mutations and recovery

Tree mutation requires an idle, fully loaded Session without pending extension input or queued prompts. Fork from an idle Session follows the same rule; Fork from a busy Session, one that is running a reply, waiting for extension input or holding queued prompts, runs in a second Pi process opened on the same session file, so the source process and its reply are never touched. That process has the source's file open, so until Pi has written the Fork's own file and its history has loaded it is not a Session: it is in neither the Runtime map nor the records, so no list, menu, command or persistence can select, stop or delete it, and no action can resolve the source's file as the Fork's. It loads the full history, since the target may lie anywhere. Only then does the Fork join the collection, with its own file. Until Pi forks, Cancel Fork from the source's message stops that process; the source cannot be deleted meanwhile. A failed or cancelled Fork disposes the process and touches no file (`SessionRegistry.#forkInNewProcess`). Targets use stable Pi entry ids and authoritative entries, never message text or browser-supplied history. Capability/preflight failure or cancellation before Pi commits preserves logical identity, history and drafts.

**Fork creates a new Provisional FrostPi identity whether the source is busy or idle.** Pi's successful Fork response is the commit boundary. For an idle source, the live Runtime follows the fork and the original id receives a stopped Runtime for its original history. The selected user message is excluded from the copied path; its validated text/images become an editable, one-shot seed, not a new persisted prompt. Presentation placement and draft handling follow the [bridge](../shared/bridge/webview-bridge.SPEC.md#authorization-and-validation) and Composer contracts.

Cancel Fork stops that child and restarts the original so a late response cannot replace recovery. If naming/state/history reconciliation fails after commit, remove the unfinished fork entry and recover the original; leave Pi-created files on disk. Rekeying Registry maps and Runtime identity must not publish a mismatched intermediate view. `SessionRegistry.forkMessage`, `#replaceRuntimeWithFork` and `#restoreOriginalAfterFork` implement this boundary.

**Tree navigation mutates the existing Pi path, not application identity.** After Pi confirms commit, its path is authoritative. Rebuild entries/state under the same Runtime and JSONL; a later load/projection failure is retryable history failure, not permission to reverse-navigate automatically. Composer replacement and non-empty-draft confirmation follow the Composer seed contract.

## Host commands on the conversation

**New conversation replaces Pi's conversation, not the application identity.** `/new` asks the running child for a new session. The FrostPi id, its presentation, the process, working directory, model and thinking level stay; Pi starts a new session on its default model, so Runtime restores the model and level that were in use. Pi's successful response is the commit boundary. Before it, a refusal or an extension veto leaves everything unchanged, restart metadata included, and the request has no deadline: an extension may ask the user first, and Pi would still commit a request FrostPi had given up on. While it is pending, Runtime refuses other requests that change or read the conversation (prompt, compaction, model, thinking level, rename, Fork, tree navigation); closing or restarting the Session stays possible and ends the request. After the boundary the earlier transcript must not stay displayed, and a failed reload is a visible history failure under the same identity. The earlier conversation stays in Pi's own session file, where Resume finds it; FrostPi neither deletes nor rewrites it. `/new` requires an idle Session without pending extension input or queued prompts. From the boundary on, the entry is Provisional again, because its new conversation has no file to restore until the first prompt, and it is retained, because the user chose to continue in it. Its record drops the earlier file at the same moment, so neither saved metadata nor a restart can reopen the conversation the user left, also when the reload failed. Starting a new conversation in an Ephemeral Session that contains a user prompt requires the same irreversible-loss confirmation as closing it.

**Reload keeps the process and the conversation.** `/reload` runs Pi's own reload through the bundled session-tree adapter, because RPC mode offers it only to an extension command. It needs an idle Session without pending extension input. Afterwards Runtime reads the command list and model catalogue again, since reloaded extensions may change both. Renaming through `/name` or `/alias` is the ordinary rename, so it also works during a turn.

**Stop ends the process, not the Session; Delete ends both and Pi's file.** Stop is the Restart path without the start: the same confirmation when a reply, tools or extension UI would be interrupted, then the Runtime stops and the Session stays listed and persisted. Selecting it, opening it in a tab, Restart or a prompt starts it again from its file; a prompt that starts it waits for the reloaded history rather than failing. Delete confirms, naming the file, then stops the Runtime and removes Pi's session file as Pi's own session picker does: to the host's trash where it has one (VS Code moves it to the Extension Host machine's trash), otherwise permanently, and only after a second confirmation when the trash refuses it. Only that file goes; other files of the session tree, such as forks, stay. A file not yet written counts as removed; a path that is not a `.jsonl` file is refused. If the file stays, the Session stays listed and stopped. Ephemeral Sessions support neither, since stopping would lose them and they have no file; they are closed instead. The UI names the operations after what they act on: **Stop Pi process** and **Restart Pi process**, with the same names on a session-list row and in the actions menu. A row shows one of them in one place, Stop while the process runs and Restart once it has stopped, disabled while it starts or stops. Delete, rare and irreversible, is offered from the actions menu and commands only, never on a list row beside Close.

**A Session created for its own presentation leaves the sidebar alone.** New-in-tab preserves the sidebar selection and does not discard the sidebar's unretained Provisional Session; with nothing selected, the new Session becomes the selection so the collection stays reachable. Asked from an existing Session, it reuses that Session's working directory only while discovery still allows the directory, and otherwise falls back to the ordinary Host choice. The presentation is told about the entry before its child starts; if the presentation cannot open, the Session still starts and the failure is reported. Such a Session may be Ephemeral: that sets what Pi saves and never where the Session is presented.

## Retention, restoration and shutdown

Provisional and Ephemeral are different policies, not successive states. New non-Ephemeral Sessions are Provisional until their first accepted non-empty prompt or explicit rename; Resume is never Provisional. Automatic fork naming and compaction do not promote it. Provisional entries are visible but excluded from restart metadata. VS Code discards the selected unretained Provisional entry when selecting/creating/resuming another Session; ever opening it in a Session Tab retains it for the rest of its provisional lifetime, including after tab closure. Desktop retains such entries for Project navigation as specified by its product contract. Discarding an entry does not delete Pi files.

An Ephemeral Session uses Pi's no-session mode for its entire lifetime. Prompts/renames cannot make it persistent. Once its process stops or fails, there is no file from which to reconstruct it: explicit and automatic restart reject it, bulk restart skips it, and Fork is unavailable. In-memory tree navigation can remain available while it is live. Closing one containing a user prompt requires an irreversible-loss confirmation.

Per-launch custom arguments are transient Runtime state, distinct from configured `frostpi.pi.arguments`. They may contain credentials and must not enter logs, persisted metadata or diagnostic exports. Restart of that Runtime reuses them; Fork's live Runtime therefore retains them, but the replacement original Runtime and later restored entries do not. Tokenization and argv construction are owned by `apps/pi-client/src/host/sessions/parseLaunchArguments.ts` and `SessionRuntime.#startInternal`, not another option validator.

The shared session index stores metadata, not conversation bodies, drafts/images, credentials, custom launch tokens or derived worktree/authorization caches. Its schema is `apps/pi-client/src/host/sessions/sessionTypes.ts`; `apps/pi-client/src/host/sessions/SessionPersistence.ts` owns serialization. On application startup, restoration recreates only indexed identities, without creating a fresh Session. `frostpi.session.startOnOpen` may start the selected restored entry according to the Host's selection policy; it is not permission to replay prompts or recover in-flight work.

Pi name events update the displayed title and shared session index. Startup repair can replace an indexed placeholder with the name stored in Pi’s JSONL, but must not persist the resume picker’s user-message preview as a session name.

Changed executable/proxy/process configuration applies on a new or explicitly restarted child, not by interrupting an existing turn. Missing, corrupt or incompatible history must fail visibly under the same identity rather than becoming a fresh conversation.

Disposal closes creation/start admission as well as live children: delayed discovery, queued starts and stale lifecycle completions must not create work after shutdown. Registry ignores Runtime change callbacks during disposal so they cannot enqueue metadata saves or interrupt Runtime cleanup. Stopping runtimes is not proof that metadata writes have drained. A file-backed Host stops runtimes, awaits `SessionRegistry.flushPersistence()`, then flushes/closes its store. Awaited save failures remain observable; fire-and-forget saves report failure without an unhandled rejection. This drains metadata, not agent turns or process snapshots.
