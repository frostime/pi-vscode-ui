# Desktop development host

This product adapts the VS Code-first [shared client](../pi-client/SPEC.md). It must use the same ClientApp, Registry, dispatch, projection and Pi RPC implementation; Project navigation is presentation/host policy, not another session manager.

## Project and session context

New Projects require validated, canonical local directories. Restored Project identities/names survive restart and temporarily unavailable paths; opening an unavailable directory fails visibly rather than silently removing its metadata. Their roots remain registered across foreground selection changes. The selected Project anchors New/Resume only; existing Pi identities/cwds do not change. The default navigation shows all open Pi, and shared UI state remains keyed by live session identity, not the currently selected Project.

The current entry is a development preview with persistent settings, Projects and saved-session metadata. Normal closing stops Pi children and drains application-state writes. Reopen does not replay prompts, resume an interrupted task, restore input requests, or recover drafts. Pi's own JSONL ownership is unchanged. Main and renderer consume the same [Desktop UI capabilities](src/shared/desktopCapabilities.ts): editor tabs, IDE selection mentions, file-reference navigation and diagnostics export are not provided. The UI hides unavailable actions or retains references as non-interactive text, while dispatch still rejects absent methods. Desktop does not register FrostPi's `/editor`; a same-named command supplied by Pi remains a Pi command.

## Application state and reopen

`state.json` sits beside `settings.json` under the FrostPi profile. The [state store](src/main/storage/DesktopStateStore.ts) owns a versioned Project list/selection plus original-key HostMemento values; the shared [SessionPersistence](../pi-client/src/host/sessions/SessionPersistence.ts) remains the session-index authority. This is metadata, not a second conversation store. Existing Provisional/Ephemeral exclusions and custom-launch-argument privacy remain governed by the [shared lifecycle](../vscode/src/extension/sessions/session-lifecycle.SPEC.md).

Startup restores Project roots before constructing Registry. Project selection remains independent from selected Pi; explicit startup directory arguments add roots and select the first supplied directory as the New/Resume anchor. Without new directory arguments, restore the saved anchor. The existing `frostpi.session.startOnOpen` starts only the selected restored Pi; false leaves all restored Pi stopped. A saved null/invalid selection stays unselected, including when the previous foreground Pi was Provisional/Ephemeral; it must not silently start the first other saved entry. Other sessions start through the normal explicit activation path. A missing/incompatible Pi history file fails visibly under the shared contract, never as a fresh conversation under the same identity.

Project and Memento updates share one serialized atomic file writer, so either field update preserves the other. Normal close stops accepting further renderer requests, stops runtimes, waits for queued Registry Memento saves, then flushes the file store before destroying the window. It does not wait for agent turns to finish or keep processes in the background. Write failures keep desired metadata in memory and the previous disk file; a later save or one flush retry can recover. A persistent close failure is reported before exit, not presented as successful restoration.

A missing state file means a new empty workspace. Invalid/unreadable state is preserved without auto-repair or reset, writes are blocked, and the UI shows the state-file error; repair externally and restart. The common JSONC reader rejects the parser's unsupported `__proto__` property instead of silently losing it. This single-main-process file store does not promise cross-process merging, task replay or power-loss recovery. Drafts/images, raw events and credentials are not application-state snapshots.

## Settings and initial import

`settings.json` lives under the system application-data directory's `FrostPi` folder. The normal launcher keeps it across exits; `FROSTPI_DESKTOP_USER_DATA` can redirect the entire profile for isolated development. Keys remain flat, original VS Code/FrostPi dot names. Real Desktop-only settings belong under `desktop.*`; Projects/window/session metadata are not settings. No Desktop-only setting is invented merely to populate that namespace.

FrostPi setting definitions come from the manifest-generated shared schema, not a second handwritten table. The [Desktop definitions](src/shared/desktopSettings.ts) add only the consumed VS Code settings: four `chat` typography keys, `editor.fontFamily`, `files.exclude`, and `search.exclude`. Shared Chat typography defaults remain single-source. Exclusion maps merge their built-in defaults with explicit entries, including `false` overrides. The Desktop maps `editor.fontFamily` to its Webview-equivalent CSS variable; it must not silently substitute `editor.fontSize` for the existing Chat code-block size semantics.

A missing Desktop settings file opens first-run setup. Import reads only the standard VS Code default-user settings file, never a Project, Remote or selected Profile. It accepts JSONC and returns an editable whitelist preview; only Save writes Desktop settings. Use defaults initializes an empty override file. Subsequent starts read Desktop settings without reimport or synchronization. Source settings and credentials are never modified. Proxy mode `vscode` converts explicitly in the preview to `custom` with a valid credential-free `http.proxy`; unresolved conversion blocks Save rather than silently changing meaning. Unsupported native notifications are skipped with a notice. Proxy credentials cannot be stored in this file.

Shared settings actions open this same settings panel. The existing `@ext:frostime.frostpi` query means the full FrostPi view; other VS Code search grammar is not implied. Network/proxy and Configure Pi target their original setting keys through a finite main-to-renderer event, never an arbitrary path. Opening the panel does not change settings or restart Pi.

The [store](src/main/settings/DesktopSettingsStore.ts) publishes changes after a successful atomic write, serializes writes, and leaves damaged/unreadable files untouched. Repair through the system editor and Reload; failed loads cannot be reset/imported/saved over automatically. Reset deletes an override rather than pinning the current default. Main owns the settings path, import path and native editor action; the renderer receives only finite sender/main-frame-validated operations. Saving refreshes typography and application configuration, never restarts Pi. Process settings apply on new/explicitly restarted children.

## Renderer and native authority

The renderer has context isolation and sandboxing with Node integration disabled. Its [preload API](src/shared/desktopBridge.ts) exposes finite client/project/dialog operations, never Node or raw IPC. Main validates sender/main-frame identity before accepting messages; common client messages additionally pass shared version/schema/session-target authorization.

Adding a Project requires a main-process native directory choice (or an explicit process-start directory argument). Renderer selection can reference only a registered identity. It cannot submit an arbitrary process cwd or configuration file path. The same rule applies while another Pi runs in the background.

Desktop pick/input responses correlate to one Host-owned request; unknown/stale ids have no effect. Only listed non-separator choices are selectable. QuickPick labels retain VS Code's `$(icon~modifier)` syntax, rendered as Codicons and text nodes rather than HTML; filtering excludes icon names and respects the caller's description/detail matching options. Separator labels remain plain text. Window disposal cancels pending interactions rather than approving them. Main owns native confirmation/file/clipboard/external-link operations; shared external links retain the http(s) check.

The renderer consumes the common client style entry and a Desktop-supplied VS Code variable palette. Packaged entry scripts and their `vendor/` resources share the VS Code Webview's entry-relative URL layout. Theme import, VS Code Workbench internals and TextMate grammar execution are not implied by that palette.

## Packaged distribution

The Windows x64 deliverable is a portable ZIP, `FrostPi-<version>-win32-x64.zip`, built with `@electron/packager` from a whitelisted staging directory: the built `dist` payload, a minimal runtime manifest whose version comes from the extension manifest, `LICENSE`, `THIRD_PARTY_NOTICES.md` extended with the Desktop runtime dependencies the shared table does not list, and an archive-root `README.txt` for users. It extracts to `FrostPi/FrostPi.exe`. No repository, sources, tests, development `node_modules`, profile data or ASAR is packaged, so Pi extension artifacts stay ordinary files on disk. Node and Pi remain machine prerequisites, and they must be discoverable from the PATH a normal desktop start receives; Electron is included, but Pi and an additional external Node installation are not. The package does not rely on a development terminal. The executable keeps the normal `FrostPi` application-data profile and is not a portable-data distribution. A single Windows x64 target is not a statement about other platforms.

Packaging reuses the installed Electron release instead of downloading another copy, and publishes both its release cache and the distributed archive through temporary files, so an interrupted run cannot leave a usable-looking artifact. Startup directories follow the packaged argument layout (`FrostPi.exe <directory>`) rather than the development launcher layout. A packaged app reports its manifest version to the client host; development leaves it unknown rather than reporting Electron's version.

## Evidence

Unit tests use temporary roots and mocked native boundaries. `test:smoke` launches actual Electron with controlled, isolated Pi children and reports explicit artifact success; a clean Electron exit alone cannot pass. `verify:package` checks the distributed archive instead: payload whitelist and version, the packaged README and third-party notices (including the license text of the Desktop-only runtime dependencies), extraction outside the repository into a path with spaces, then the real packaged executable through its shared UI with an isolated profile and a controlled Pi. `verify:package --real-pi` additionally starts the installed Pi from the reconstructed machine/user PATH in its own profile and ephemeral session, and drives one temporary extension command through the shared confirmation and conversation UI with no model access and no credentials; history persistence and Stop stay covered by the controlled phase. The PATH proof reconstructs configured machine/user values, not a particular Explorer session's potentially stale environment. Real model turns, durable real-Pi history/streaming Stop, signing and publication remain separate acceptance work.
