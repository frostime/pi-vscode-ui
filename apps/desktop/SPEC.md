# Desktop development host

This product adapts the VS Code-first [shared client](../pi-client/SPEC.md). It must use the same ClientApp, Registry, dispatch, projection and Pi RPC implementation; Project navigation is presentation/host policy, not another session manager.

## Project and session context

New Projects require validated, canonical local directories. Restored Project identities/names survive restart and temporarily unavailable paths; opening an unavailable directory fails visibly rather than silently removing its metadata. Their roots remain registered across foreground selection changes. The selected Project is the browsing and New/Resume context: its last-viewed Session is selected, or its empty state is shown. The shared Header lists only that Project's open Sessions; Desktop owns the Project list and aggregate running/input indicators instead of a second global Session list. Existing Pi identities/cwds do not change, and shared UI state remains keyed by live session identity, not Project.

New/Resume associates the opened identity with the Project that initiated the action, including sessions in linked git worktrees; cwd does not choose or change that owner. Resuming an already-open file reuses the same Runtime and associates it with the requesting Project, rather than creating another process for that file. Forks inherit their source's Project. A late result after a Project switch stays in its originating Project and must not replace the newly foregrounded chat. These associations belong only to Desktop metadata, not the shared Session record or RPC schema.

Selecting or adding a Project must not leave another Project's conversation visible. Adding a directory immediately selects it without creating Pi. Project navigation retains in-memory Provisional Sessions so unsent drafts survive switching; they remain excluded from restart metadata. Sidebar hide/resize changes only the shell, never the ClientApp mount. At narrow widths the sidebar becomes a temporary drawer, and hidden navigation retains a reachable restore/input-attention entry.

Removing a Project closes its owned Sessions before unregistering its root, without deleting the directory or Pi history. Confirmation covers discarded drafts and temporary conversations; shared close/Fork guards still apply. Cancelled or failed closes retain the Project rather than hiding live Sessions. Removing the selected Project leaves no foreground Project or Session; removing another Project preserves the current foreground. Pending New/Resume must finish or be cancelled before removal, so a late result cannot create an orphaned Session.

The current entry is a development preview with persistent settings, Projects and saved-session metadata. Normal closing stops Pi children and drains application-state writes. Reopen does not replay prompts, resume an interrupted task, restore input requests, or recover drafts. Pi's own JSONL ownership is unchanged. Main and renderer consume the same [Desktop UI capabilities](src/shared/desktopCapabilities.ts): editor tabs, IDE selection mentions and diagnostics export are not provided. The UI hides unavailable actions or retains references as non-interactive text, while dispatch still rejects absent methods. Desktop does not register FrostPi's `/editor`; a same-named command supplied by Pi remains a Pi command.

## Application state and reopen

`state.json` sits beside `settings.json` under the FrostPi profile. The [state store](src/main/storage/DesktopStateStore.ts) owns a versioned Project list/selection plus original-key HostMemento values; the shared [SessionPersistence](../pi-client/src/host/sessions/SessionPersistence.ts) remains the session-index authority. Desktop's `frostpi.desktop.navigation.v1` Memento value stores Project associations, per-Project last-viewed ids and sidebar layout. Navigation persistence must filter identities through shared SessionPersistence, so Ephemeral/Provisional ids and drafts do not leak into restart state. This is metadata, not a second conversation store. Existing Provisional/Ephemeral exclusions and custom-launch-argument privacy remain governed by the [shared lifecycle](../pi-client/src/host/session-lifecycle.SPEC.md).

Startup restores Project roots before constructing Registry. Explicit startup directories select the first supplied Project; otherwise restore the saved Project context. The first migration of old, ungrouped metadata associates exact cwd matches with their registered Projects and unmatched worktree entries with the saved anchor; it follows the actual saved foreground Session to eliminate the old anchor/chat mismatch. Explicit startup directories take priority over that migration. Existing navigation metadata keeps its Project selection. The existing `frostpi.session.startOnOpen` starts only the selected restored Pi; false leaves all restored Pi stopped. A saved null/invalid selection stays unselected, including when the previous foreground Pi was Provisional/Ephemeral; it must not silently start the first other saved entry. Other sessions start through the normal explicit activation path. A missing/incompatible Pi history file fails visibly under the shared contract, never as a fresh conversation under the same identity.

Project and Memento updates share one serialized atomic file writer, so either field update preserves the other. Normal close stops accepting further renderer requests, stops runtimes, waits for queued Registry Memento saves, captures the filtered Desktop navigation metadata, then flushes the file store before destroying the window. It does not wait for agent turns to finish or keep processes in the background. Write failures keep desired metadata in memory and the previous disk file; a later save or one flush retry can recover. A persistent close failure is reported before exit, not presented as successful restoration.

A missing state file means a new empty workspace. Invalid/unreadable state is preserved without auto-repair or reset, writes are blocked, and the UI shows the state-file error; repair externally and restart. The common JSONC reader rejects the parser's unsupported `__proto__` property instead of silently losing it. This single-main-process file store does not promise cross-process merging, task replay or power-loss recovery. Drafts/images, raw events and credentials are not application-state snapshots.

## Settings and initial import

`settings.json` lives under the system application-data directory's `FrostPi` folder. The normal launcher keeps it across exits; `FROSTPI_DESKTOP_USER_DATA` can redirect the entire profile for isolated development. Keys remain flat, original VS Code/FrostPi dot names. Real Desktop-only settings belong under `desktop.*`; Projects/window/session metadata are not settings. No Desktop-only setting is invented merely to populate that namespace.

FrostPi setting definitions come from the manifest-generated shared schema, not a second handwritten table. The [Desktop definitions](src/shared/desktopSettings.ts) add only the consumed VS Code settings: four `chat` typography keys, `editor.fontFamily`, `files.exclude`, and `search.exclude`. Shared Chat typography defaults remain single-source. Exclusion maps merge their built-in defaults with explicit entries, including `false` overrides. The Desktop maps `editor.fontFamily` to its Webview-equivalent CSS variable; it must not silently substitute `editor.fontSize` for the existing Chat code-block size semantics.

A missing Desktop settings file opens first-run setup. Import reads only the standard VS Code default-user settings file, never a Project, Remote or selected Profile. It accepts JSONC and returns an editable whitelist preview; only Save writes Desktop settings. Use defaults initializes an empty override file. Subsequent starts read Desktop settings without reimport or synchronization. Source settings and credentials are never modified. Proxy mode `vscode` converts explicitly in the preview to `custom` with a valid credential-free `http.proxy`; unresolved conversion blocks Save rather than silently changing meaning. Unsupported native notifications are skipped with a notice. Proxy credentials cannot be stored in this file.

Settings use one modal with broad category navigation and multiple grouped containers per page. Renderer presentation metadata supplies labels, descriptions and grouping, not another key/default/type schema. The schema-to-presentation coverage test must include new settings exactly once; add Desktop-only definitions under `desktop.*` and place them in the appropriate visual group. Labels are the normal surface; full keys remain searchable and available through keyboard-reachable detail/copy controls. Display units may differ from stored units without changing the original value semantics.

The settings draft belongs to the open panel, survives category/search changes and failed saves, and is not live configuration. Import remains an unsaved preview. Save/Discard are explicit; closing or reloading an edited form requires discard confirmation. Background settings-view refreshes must not replace edited fields. A failed load stays read-only until external repair and Reload; drafts are not a cross-restart store.

Shared settings actions open this same settings panel. The existing `@ext:frostime.frostpi` query means the full FrostPi view; other VS Code search grammar is not implied. Network/proxy and Configure Pi target their original setting keys through a finite main-to-renderer event, never an arbitrary path. Opening the panel does not change settings or restart Pi.

The [store](src/main/settings/DesktopSettingsStore.ts) publishes changes after a successful atomic write, serializes writes, and leaves damaged/unreadable files untouched. Repair through the system editor and Reload; failed loads cannot be reset/imported/saved over automatically. Reset deletes an override rather than pinning the current default. Main owns the settings path, import path and native editor action; the renderer receives only finite sender/main-frame-validated operations. Saving refreshes typography and application configuration, never restarts Pi. Process settings apply on new/explicitly restarted children.

## Desktop Resume presentation

Resume uses a Desktop-only conversation-area overlay, not a generic status bubble, notification center or rendering of every `withProgress` call. Keep its finite presentation transport, async interaction attribution and CSS in `apps/desktop`; the shared ClientApp, Registry lifecycle and VS Code native progress UI remain unchanged. Resume still enters through the schema-validated sidebar Connection; panel rejection and ordinary action authorization must not be bypassed by the Desktop dispatcher.

The overlay retains the mounted shared conversation and Composer. Its Desktop geometry binding to `.conversation-frame` must be rechecked when the shared shell layout changes; when no conversation exists yet, it covers the empty client surface instead. An expanded Composer has no conversation space, so only in that layout the overlay covers `.composer-region` instead. It must not minimize the Composer, remount its editor or rewrite its draft; Escape belongs to the Resume selection rather than the expanded Composer underneath. It does not create another ClientApp or take over Session state. Switching to another Pi hides only this presentation and leaves a Resume-specific return action; it neither cancels the pending picker nor pauses background Pi work.

Busy feedback begins before discovery, without needing a Runtime. A Host-owned selection is not process recovery and has no busy animation; native file/confirmation choices retain their existing authority. Only interactions from the actual Resume async scope may be embedded in its picker, never concurrent unrelated Host selections or a title-text guess. Startup readiness does not mean history is loaded: follow the returned Session id, not whichever Pi is now foreground. Deferred history returns to the existing shared busy/history UI, without claiming that the history loaded. Failure remains readable; busy work has no pretend Cancel, and dismissal is limited to the matching failed presentation. No simulated substeps, percentages, automatic retries or persisted task state are implied.

## Renderer and native authority

The renderer has context isolation and sandboxing with Node integration disabled. Its [preload API](src/shared/desktopBridge.ts) exposes finite client/project/dialog operations, never Node or raw IPC. Main validates sender/main-frame identity before accepting messages; common client messages additionally pass shared version/schema/session-target authorization.

Adding a Project requires a main-process native directory choice (or an explicit process-start directory argument). Renderer selection can reference only a registered identity. It cannot submit an arbitrary process cwd or configuration file path. The same rule applies while another Pi runs in the background.

Desktop pick/input responses correlate to one Host-owned request; unknown/stale ids have no effect. Only listed non-separator choices are selectable. QuickPick labels retain VS Code's `$(icon~modifier)` syntax, rendered as Codicons and text nodes rather than HTML; filtering excludes icon names and respects the caller's description/detail matching options. Separator labels remain plain text. Window disposal cancels pending interactions rather than approving them. Main owns native confirmation/file/clipboard/external-link operations; shared external links retain the http(s) check.

File references resolve against the displayed Session cwd, not the selected Project or main-process cwd. Desktop reuses the shared reference whitelist and validates existing local targets in main, including symlink targets; unknown file types are rejected even for explicit Markdown links. Recognized code/configuration files, including script-capable HTML/SVG, open only through a main-constructed VS Code file URI. It preserves line/column where present; a line range opens at its start without range selection. A failed editor launch must not fall back to a potentially executing default file association. Ordinary documents/media and actual directories use the system default application without line/range targeting; opening a directory does not register a Project. Desktop does not perform VS Code's missing-file search fallback or accept arbitrary application protocols.

The renderer consumes the common client style entry. Desktop's built-in Dark Modern and Light Modern palettes supply VS Code variables, including the shared code-highlight colors; `desktop.theme` defaults to `dark` and persists the manual choice independently of VS Code and the OS. The sidebar toggle waits until first-run settings are saved or defaults are chosen, so appearance changes cannot consume the one-time import offer. Apply the saved scheme before mounting the client. Live switching updates native controls, dialogs and mounted diagrams without remounting ClientApp or discarding drafts, disclosure or scroll state. It never restarts Pi. Theme import, VS Code Workbench internals and TextMate grammar execution remain out of scope.

Packaged entry scripts and their `vendor/` resources share the VS Code Webview's entry-relative URL layout.

## Packaged distribution

The Windows x64 deliverable is a portable ZIP, `FrostPi-<version>-win32-x64.zip`, built with `@electron/packager` from a whitelisted staging directory: the built `dist` payload, a minimal runtime manifest whose version comes from the extension manifest, `LICENSE`, `THIRD_PARTY_NOTICES.md` extended with the Desktop runtime dependencies the shared table does not list, and an archive-root `README.txt` for users. It extracts to `FrostPi/FrostPi.exe`. No repository, sources, tests, development `node_modules`, profile data or ASAR is packaged, so Pi extension artifacts stay ordinary files on disk. Node and Pi remain machine prerequisites, and they must be discoverable from the PATH a normal desktop start receives; Electron is included, but Pi and an additional external Node installation are not. The package does not rely on a development terminal. The executable keeps the normal `FrostPi` application-data profile and is not a portable-data distribution. A single Windows x64 target is not a statement about other platforms.

Packaging reuses the installed Electron release instead of downloading another copy, and publishes both its release cache and the distributed archive through temporary files, so an interrupted run cannot leave a usable-looking artifact. Startup directories follow the packaged argument layout (`FrostPi.exe <directory>`) rather than the development launcher layout. A packaged app reports its manifest version to the client host; development leaves it unknown rather than reporting Electron's version.

## Evidence

Unit tests isolate native adapters and file stores. `test:smoke` exercises the built renderer in actual Electron with controlled Pi children; `verify:package` exercises the distributed archive's extracted executable, not the development launcher. Both require explicit success artifacts and isolated data. Test ownership and evidence limits, including optional `--real-pi`, are defined in [testing.md](../../.dev/docs/testing.md#evidence-boundaries); delivery commands and gates are in [release.md](../../.dev/docs/release.md#desktop-candidate-packaging-windows-x64).

Packaged PATH verification uses configured machine/user values without injecting the developer's Node directory. It does not reproduce a particular Explorer process's potentially stale environment.
