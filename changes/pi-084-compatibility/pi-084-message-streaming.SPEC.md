# 问题

FrostPi 启动用户环境中的 Pi，不捆绑也不固定 Pi 版本。Pi 0.83 和 Pi 0.84 对实时助手消息采用了不同的 RPC 事件格式：

- Pi 0.83 的 `message_update` 带有当时已经生成的完整助手消息；
- Pi 0.84 的 `message_update` 只带有某个内容块的位置和本次新增的内容。

FrostPi 当前要求每次 `message_update` 都带有完整助手消息，因此会忽略 Pi 0.84 的更新事件。最终回复通常仍会在 `message_end` 后出现，但在生成结束前看不到实时文本、思考内容和正在生成的工具参数。

本次修改的目标是同时支持这两种事件格式，并在 Pi 0.84 下尽量保持 Pi 0.83 已有的实时页面行为。成功标准不只是“最终消息能出现”，还包括生成过程连续、工具卡不重复、展开状态不丢失，以及异常中断后不把上一次生成的临时内容带入下一次生成。

# 解决方向

在扩展端把 Pi 消息转换为页面内容的位置，增加一个 Pi 助手消息适配器。它通过有状态的内容拼接，把两个版本的事件转换成 FrostPi 内部统一的数据：

- 收到 Pi 0.83 的完整消息时，直接采用该完整消息；
- 收到 Pi 0.84 的分段更新时，按 `contentIndex` 将文本、思考内容和工具参数拼成当前完整内容；
- 将拼好的当前内容交给现有的会话内容处理逻辑；
- 收到 `message_end.message` 后，以它替换临时拼接结果；
- Pi 的持久化 `get_entries` 结果仍然优先于所有实时事件。

这段逻辑属于 VS Code 扩展的会话内容处理层。通用 RPC 包继续原样传递 Pi 事件；页面端继续只接收扩展端整理后的数据。

# 对外行为

## Pi 0.83

- 当 `message_update.message` 是合法的助手消息时，FrostPi 直接采用这份累计内容。
- 同一事件中的 delta 不再用于追加内容，避免同一段内容出现两次。
- 旧事件中的错误或中止信息仍可用于保持现有的消息状态行为。
- 现有的实时文本、思考内容和结构化工具参数展示不应退化。

## Pi 0.84 文本和思考内容

- `message_start.message` 提供本次助手消息的初始信息。
- `text_start`、`text_delta`、`text_end` 更新对应 `contentIndex` 的文本块。
- `thinking_start`、`thinking_delta`、`thinking_end` 更新对应 `contentIndex` 的思考内容块。
- 多个内容块可以交错更新；页面顺序按 `contentIndex` 确定。
- `text_end.content` 和 `thinking_end.content` 替换对应内容块此前临时拼出的文字。
- 同一内容块在多次更新之间保持相同的页面条目 ID，避免折叠状态或页面局部状态被重置。

## Pi 0.84 工具调用

- 收到 `toolcall_start` 后，页面立即出现一张“准备工具调用中”的卡片。
- 卡片可以展开；`toolcall_delta.delta` 到达时，展开区域持续显示当前累计的原始参数文本。
- 在 `toolcall_end` 之前，Pi 0.84 没有提供真实工具 ID 和工具名称，因此页面不得猜测具体工具。
- 收到 `toolcall_end.toolCall` 后，同一张卡片原地更新为真实工具卡，显示真实 ID、名称和完整的结构化参数。
- 从准备阶段变为真实工具卡时，不得创建第二张卡片，不得收起用户已经展开的卡片。
- 后续 `tool_execution_start`、`tool_execution_update`、`tool_execution_end` 必须继续更新这张卡片。
- 多个工具调用分别按自己的 `contentIndex` 保存参数和页面身份，不能互相覆盖。

## 最终内容和历史内容

内容发生冲突时，按以下顺序决定页面应采用什么：

1. 分段更新只用于生成过程中的临时预览；
2. `message_end.message` 决定该次实时助手消息的最终内容；
3. `get_entries` 返回的持久化记录决定恢复、刷新和接管后的会话历史。

如果 `message_end.message` 与临时拼接结果不同，页面必须改为最终消息。持久化记录已经接管某个助手消息后，延迟到达的实时更新不得再次改变内容或移动页面条目。

## 正常结束、中止和进程失败

- `message_end` 结束当前临时拼接状态。
- 新的助手 `message_start` 开始新的拼接状态；上一条没有闭合的临时状态不能污染新消息。
- `agent_settled`、完整历史替换、当前一轮对话被显式结束、进程停止、连接失败和进程重启都必须清理临时拼接状态。
- 自动重试中的每次新助手消息分别拼接；失败尝试和后续成功尝试不能共用内容缓存。
- 如果权威的最终消息不包含此前临时显示的工具调用，该临时工具卡应随最终内容替换而消失。
- 如果进程在最终消息到达前停止或失败，已经显示的准备中工具卡保留，状态改为 `cancelled`，并保留已经收到的原始参数文本。
- 后续完整历史刷新仍以 Pi 的持久化记录为准。

## 不完整或顺序异常的事件

以下事件不应导致 RPC 连接失败，也不应向会话页面添加警告：

- `contentIndex` 缺失、不是非负整数或无法对应内容块；
- 某个内容块尚未开始便收到 delta 或 end；
- 同一 `contentIndex` 的内容类型前后冲突；
- 未识别的助手消息 delta；
- 缺少必要字段、无法与当前助手消息关联的 update。

FrostPi 忽略这些局部异常，等待合法的 `message_end` 或持久化刷新恢复页面。一个合法的完整 `message_end` 即使没有对应的 `message_start`，仍应正常显示。

JSONL 无法解析、RPC 顶层记录不合法、进程退出或连接读写失败仍按现有规则作为可见的连接错误处理。本次修改不放宽传输层错误。

# 实现决定

- 兼容判断依据事件是否带有合法的完整助手消息，不依据 Pi 版本号。
- 完整助手消息和分段更新同时存在时，完整助手消息决定内容；分段更新不得再次追加相同内容。
- 临时消息状态由会话内容处理层拥有，并集中封装在 Pi 助手消息适配器中。它不能放入通用 RPC 包，也不能转移到页面端。
- 适配器的架构职责是消除 Pi 0.83 与 0.84 的消息事件差异；它采用的具体方法是按 `contentIndex` 拼接分段内容。
- 每个 `contentIndex` 对应一个明确类型的内容块。文本、思考内容和工具调用分别保存，最终按数字顺序输出。
- 工具卡在页面中的条目 ID 不能依赖尚未到达的真实 `toolCall.id`。页面条目 ID 从准备阶段到持久化记录接管期间保持稳定；真实工具 ID 只用于关联 Pi 的工具执行事件。
- 准备中工具卡需要保存原始参数文本。真实工具信息到达后，完整结构化参数替换准备阶段的参数预览。
- 工具执行状态、输出、结束时间和持久化工具结果继续遵循现有的会话条目存储规则；本次修改不重新设计工具执行模型。
- 每个 Pi 更新事件仍产生一次对应的页面数据更新。本次不增加节流、批处理或参数大小限制。
- 不记录提示词、回复正文、工具参数、图片、凭据或其他敏感内容。

# 验收标准

## 自动验证

- Pi 0.83 风格的累计 `message_update` 连续到达时，文本和工具参数不会重复追加，现有实时行为保持不变。
- Pi 0.84 风格、只带分段内容的更新可以在 `message_end` 前显示实时文本和思考内容。
- 多个、交错更新的 `contentIndex` 按正确顺序显示，并在更新之间保持稳定的页面条目 ID。
- `text_end`、`thinking_end` 和 `message_end` 可以纠正与临时累计结果不一致的内容。
- 工具调用从准备卡、原始参数增长、真实工具绑定到工具执行结束始终只有一张卡片，且页面条目 ID 不变。
- 多个准备中的工具调用不会混用参数或真实工具 ID。
- 持久化记录接管后，延迟的实时 update/end 不会覆盖持久化内容或移动条目。
- 自动重试、中止、`agent_settled`、完整历史替换、进程停止、连接失败和重启不会把旧的临时内容带入下一次助手消息。
- 进程在工具信息完成前中断时，准备卡保留为 `cancelled` 并保留已收到的原始参数。
- 不完整或顺序异常的 delta 按本规范忽略；后续合法最终消息仍能正常显示。
- 测试用 Pi 进程通过真实 JSONL/RPC 路径发出 Pi 0.84 风格的完整事件序列，并验证扩展端能把它实时显示到会话页面，而不只是验证传输层收到事件。
- 相关单元测试、定向 VS Code 测试和仓库检查命令通过。

## 页面检查

- 准备中工具卡可以展开，原始参数更新时保持展开。
- 真实工具信息到达后，卡片原地更新，无闪烁、重复卡片或折叠状态丢失。
- 页面在 280px 宽度下可用，并适配 VS Code 的浅色、深色和高对比度主题。

# 不在本次范围内

- 检测或限制外部 Pi 版本；
- 修改 Pi SDK、Provider、OAuth、Harness、Remote Client 或 Session Repository API；
- 修改 Pi session JSONL 格式或 FrostPi 的会话目录扫描；
- 在页面端处理原始 Pi 事件；
- 为流式更新增加节流、批处理或参数大小限制；
- 要求真实 Provider 和凭据参与自动化测试；
- 保证用户自己的 Pi extensions 或 Provider 与 Pi 0.84 兼容。

真实 Pi 0.84 二进制和真实 Provider 的运行验证可以后续补充，不作为本次修改完成的最低条件。

# 本文用语

- **Pi 助手消息适配器**：本次代码修改中的专用组件。它把 Pi 0.83 的累计消息事件和 Pi 0.84 的分段消息事件转换成 FrostPi 内部统一的数据。按位置拼接内容是它完成适配的方法；它不处理会话轮次、页面条目位置或工具执行。
- **累计助手消息**：在某一时刻，把已经收到的所有分段更新拼在一起后得到的完整助手消息。它只用于实时页面，不是持久化历史。
- **准备中工具卡**：已经知道模型开始生成工具调用，但尚未收到真实工具 ID 和名称时显示的工具卡。它显示通用标题和当前原始参数。
- **分段更新（delta）**：Pi 在一次 `message_update` 中发送的新增文本、思考内容或工具参数片段，不代表当时的完整助手消息。
- **页面条目 ID**：页面端用来判断“这是原来那一项的更新，而不是新的一项”的稳定标识。它与 Pi 用来关联工具执行事件的真实工具 ID 不是同一个概念。
- **持久化记录接管**：Pi 已把消息写入 session，并由 `get_entries` 返回后，FrostPi 用该记录替换此前临时页面内容的过程。
